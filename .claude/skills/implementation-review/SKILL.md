# 実装レビュー / 受け入れ判定

実装した本人が「直したのでOK」と自己判断で完了にしないための手順。判定の根拠は**成果物と Work Item（依頼の原文）と ADR だけ**。組み込みの `/code-review`（バグ・簡素化の観点）は置き換えず、呼ぶ側に回る。

## Step 1: 材料を束ねて深さを決める

```bash
python3 scripts/review_bundle.py --work docs/work-items/WORK-<slug>.md
# Work Item が無いとき: 依頼の原文と受け入れ条件を書いたファイルを --request で渡す
```

出力は `bundle:`（材料のパス）と `depth:`（深さと理由）の数行だけ。材料（依頼の原文・Work Item・関係するADR・チェックリスト・CLAUDE.md の固有の約束事・差分）は `.git/ai-review/bundle.md` にまとまっている。**自分でこれを開いて読み直さない。**

| depth | やること |
| --- | --- |
| `session` | `/code-review` を1回 + bundle のチェックリストで自分が判定（Step 3 の形式で） |
| `agent` | Step 2 |

ユーザーが「軽く見て」と言えば `session` に落としてよい。理由に「認証・権限…」が出て実際にそこを変えているなら、あわせて `go-live-checklist` の要否を聞く。

## Step 2: 別エージェントに判定させる

Agent ツールで `impl-reviewer` を起動する。プロンプトは次だけにする。

```
レビューの材料: .git/ai-review/bundle.md
このファイルだけを根拠に判定する。差分だけでは判断できない箇所に限ってリポジトリのファイルを開く。
```

**渡さないもの**: 実装時の判断理由・事情・自己評価。追認に引きずられる。diff を書き写さない（同じ内容を2回流すことになる）。

## Step 3: 判定の基準

- 観点ごとに **満たす / 満たさない** と根拠（ファイルと行）。点数は付けない
- **受け入れ = 満たさない観点が1つも無い**
- **「ほぼ満たしている」は満たさない。** Work Item の数値・条件をわずかでも下回れば満たさない
- **承認済みのADRとの食い違いは見送れない。** ユーザーが押し切っても正しいとしない。コードを直すか、`new_doc.py adr <slug> --supersedes ADR-old` で新しいADRを起こす
- 観点は bundle の既定8つ + CLAUDE.md「固有の約束事」。未記入なら既定だけで判定し、その旨を報告に書く。推測で観点を作らない
- 観点を減らすのは原理的に成立しないときだけ。増減したら CLAUDE.md に書いて固定する

## Step 4: 修正ループ

1. `impl-reviewer` が修正チケット（問題・直し方・該当箇所・**解消の確認方法**）を出す。チケットをファイルに保存する（例: `.git/ai-review/tickets.md`）
2. 実装担当がチケットに沿って直す
3. `python3 scripts/review_bundle.py --recheck .git/ai-review/tickets.md` で**初回以降の修正分だけ**を束ね、`impl-reviewer-recheck` に出力のパスだけを渡す
4. 未解消があれば 2 へ。ループは5回まで。超えたら詰まっている点を添えて人間に報告する

指摘に反論があるなら握りつぶさず人間に上げる。**見送る指摘**は、ユーザーの了承を得たうえで「観点・ファイル・理由」を Work Item の「決めたこと」に1行で残す（ADRとの食い違いは除く）。

## Step 5: 結果を伝える

観点ごとの判定と根拠・受け入れ可否・見送った指摘。受け入れたら `work-log` を案内する。エージェントのレビューを通ったものだけを人間のレビューに回す。
