# ワークツリー分割による並列実装

**既定は直列。** ユーザーが明示的に並列を求めたときだけ使う。並列は人数分だけ文脈を複製し、レビューも人数分になる、最もトークンを使う進め方。

## Step 1: 分割してよいか

分割するのは、独立して実装・レビュー・マージできる機能が2つ以上あるときだけ。次のどれかに当たれば理由を伝えて直列を提案する: 機能が1つ / AがBの前提（依存）/ 同じファイル・層を大きく書き換える / DBマイグレーションを含む（単独で先にマージ）。判定と理由は Work Item の「並列化の単位」に書き（機能ごとに Work Item を分け）、**承認を得てから作る**。

## Step 2: 作る（スクリプト）

```bash
python3 scripts/worktree_setup.py <機能名>     # 英小文字・数字・ハイフン
```

`../<repo>-worktrees/<機能名>` にブランチ `feature/<機能名>` を作り、ロックファイルから判定したコマンドで依存を入れる。1ワークツリー = 1ブランチ = 1PR、5つまで（超えるならスクリプトが止まるので人間に確認）。

失敗した・判定できないと出たら、直さずに並列を始めない。スクリプトが出す注意も守る:

- `.env` 等の git 管理外ファイルは新しいツリーに無い。**中身を読んでコピーしない**。どのファイルが要るかをユーザーに伝える
- ローカルDB・キャッシュはツリーごとに別物。他のツリーのDBを参照・コピーしない
- devサーバを同時に起動するなら、CLAUDE.md のポートの変え方でずらす。**空欄なら推測せず聞く**

## Step 3: 並列で実装する

- 機能ごとに担当を1つ、**担当ツリーの中だけ**で作業させる。渡すのはその機能のスコープ / スコープ外 / 受け入れ条件だけ（ファイルのパスで。AGENTS.md「委譲するとき」）
- 他機能への依存が分かったら、他のツリーを触らず止めて報告する。共通処理は独断で寄せず確認する
- `main` の取り込みは `git merge`。rebase や履歴を書き換える操作は使わない

## Step 4: レビューと統合

`implementation-review` を**機能ごとに**行う（ループ上限も機能ごと）。複数機能を1つのPRにまとめない。

## Step 5: 後始末（列挙するだけ）

PRがマージされ `work-log` を残した機能から順に:

```bash
python3 scripts/worktree_setup.py --list
```

削除してよいもの（マージ済み・未コミットの変更なし）を報告に並べ、**削除は人間に頼む**（`git worktree remove` / `prune` は安全ルール1でブロックされる）。
