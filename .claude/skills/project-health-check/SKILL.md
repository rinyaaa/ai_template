# Project Health Check

やるべきことを優先度付きの短いリストにして、次の行動につなげる。異常が無ければ「異常なし」の一言で終えてよい（毎回長いレポートは読まれなくなる）。週1回を想定。

## Step 1: 集める（スクリプト1回）

```bash
python3 scripts/health_check.py      # 遅ければ --no-audit
```

安全網の自己点検・Dependabot PR・セキュリティアラート・CI失敗・放置PR・未コミット/未push・マージ済みブランチ・依存の脆弱性・派生プロジェクトの未記入を1回で集め、「今すぐ / 今週中 / 気に留めておく / 見ていない項目」に仕分けて出す。**出力の要約だけを使い、同じ `gh` / `git` を手で叩き直さない。** 詳しく見る必要がある項目だけ個別に調べる。

CLAUDE.md に lint/test コマンドがあれば、ここで実行して結果を足す。

## Step 2: スクリプトが判断しないもの

- **安全網の自己点検の失敗は最優先**。何がいつから守られていなかったかを平易に伝え、テンプレートの状態への復旧を提案する
- **secret-scan の失敗は一括対応しない**。本物の秘密情報か確かめ、本物ならキーの無効化・再発行を先にする。誤検知と確認できたときだけ `.gitleaks.toml` に allowlist を足す。判断できなければ、そのことを伝えて止まる
- **digest 固定の docker image**（`run:` の中など、Dependabot の対象外）は最新版を調べて遅れていれば提案する。上げる前に `gh api repos/<owner>/<repo>/license --jq .license.spdx_id` で**ライセンスが変わっていないか**確かめ、変わっていたら固定し直さずユーザーに判断を仰ぐ（例: gitleaks-action v2 は独自ライセンスになり、Organization で登録が要るようになった）
- **派生プロジェクトの未記入**は、使わない機能なら問題にしない。night-run を使う予定があるかを聞いてから優先度を付ける
- 「見ていない項目」は「問題なし」と言い換えない

## Step 3: 報告する

3段階（今すぐ / 今週中 / 気に留めておく）+ 見ていない項目。技術用語には一言の説明、各項目に具体的な次の一手を添える（例:「『DependabotのPRを取り込んで』と言ってもらえれば、CIが通っているか確かめて取り込みます」）。頼まれたらその場で対応してよいが、Dependabot PR の取り込みは CI 結果（無ければローカルの test）を確かめてから。ブランチの削除はしない（`/clean_gone` を案内する）。

## Step 4: 記録する

日付と主な結果を1〜3行で `docs/health-check-log.md` に追記する（無ければ作成を提案）。前回からの差分（「2件→5件」）は単発の数字より意味があるので、記録があれば必ず比べる。
