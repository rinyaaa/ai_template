# Safe Rollback

最優先は「元に戻すこと」ではなく「**これ以上悪化させないこと**」。今ある状態は、消さない限り後から調べ直せる。

## 大原則

1. **消さない・上書きしない。** 使ってよいのは追加する操作（ブランチ作成・revert コミット）だけ。`git reset --hard`・`git clean`・`git checkout -- .`・`git restore`・force push は使わない
2. **先に退避する。** どの手段でも、Step 1 の `--save` を済ませてから
3. **1操作ごとに平易に説明する。** 何をするか・何が起きるか・失敗してもやり直せるか
4. **2回試して直らなければ手を止める。** 現状・試したこと・残る選択肢を整理して報告する

## Step 1: 把握して退避する（スクリプト1回）

```bash
python3 scripts/rollback_snapshot.py --save
```

ブランチ・未コミットの変更・最近のコミット・stash・未push を要約し、**作業ツリー丸ごと（未追跡を含む）を `backup/before-rollback-<日時>` ブランチに退避**する。作業ツリーと今のブランチは変えない。ユーザーには「今の状態を `backup/...` に保存したので、この後何が起きても今の時点に戻れます」と伝える。

あわせて「いつまで動いていたか」「壊れる直前に何をしたか（自分の操作・AIへの依頼・デプロイ）」を聞き、エラーやスクリーンショットがあれば見せてもらう。

## Step 2: どこが壊れているか切り分ける

| 状況 | 見分け方 | 戻し方 |
| --- | --- | --- |
| A. 未コミットの変更 | 最後のコミット時点では動いていた | `git stash push -u -m "壊れた変更 <日付>"`（捨てずに退避。stash は消さない） |
| B. コミット済み・未push | 壊した変更がローカルのコミットにある | `git revert <コミット>`（複数なら `git revert --no-commit <古い方>..HEAD` で1つに） |
| C. push済み | リモートにも上がっている | ローカルで revert → 通常の `git push`。PR運用なら revert も PR で |
| D. 本番デプロイ | 本番でエラー | **ホスティングの「前のデプロイに戻す」を先に案内**（コード修正→再デプロイより速く確実）。手段が無ければ B/C で戻して再デプロイ |
| E. DBマイグレーション | 実行後からデータが見えない・消えた | 下記 |

どのコミットから壊れたか不明なら、`git log` とユーザーの記憶（「この日は動いていましたか」）を突き合わせて絞る。過去のコミットで試すときも Step 1 の退避の後で。

**E だけは慎重さを一段上げる。** down migration か直前のバックアップがあるかを先に確かめ、**どちらも無い、または巻き戻しがデータ削除を伴うなら実行せず止まる**。状況を整理し、DBホスティングのバックアップ機能（ポイントインタイムリカバリ等）やサポートを案内する。実行するときも、何が起きるかを平易に説明して明示の承認を得てから（AGENTS.md ルール4の形式）。

## Step 3: 直ったか確かめる

CLAUDE.md のテスト・起動コマンドで、ユーザーが訴えた症状が消えたことを確かめる（可能ならユーザー自身にも見てもらう）。手段が無ければ正直にそう伝える。

## Step 4: まとめる

- 原因（分かった範囲で。分からなければそう言う）
- 何をどこまで戻したか
- 壊れた状態の退避先（`backup/...`・stash）と、原因調査に使えること
- 再発防止に次にやるとよいこと

退避ブランチ・stash は、ユーザーが「もう要らない」と明言するまで消さない。
