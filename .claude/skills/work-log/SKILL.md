# 作業記録（history）

**同じ詰まり方を二度しない**のが目的で、進捗報告書ではない。

**重要な前提**: `docs/history/` は、次のタスクを始めるときに読まれない。読む仕組みを意図的に作っていない（大半の記録は次のタスクと無関係で、毎回読むとコストだけがかかるため）。したがって**記録を書くこと自体では、次回の挙動は変わらない**。挙動を変えるのは Step 3 の昇格だけ。ここを飛ばすと、この作業は人間向けのログを書いただけで終わる。

## いつ書くか

レビューを通って作業が一区切りしたとき。PRを出したなら、マージを待たずに書いてよい。

**書かなくてよいもの**: タイポ修正、設定値の変更、調査だけで終わった依頼。詰まりも知見も無い作業を記録しても、後から読む人のコストになるだけ。

## 書き方

`docs/history/YYYY-MM-DD-<タスクの短い名前>.md`（日付は `date +%F` で取る）。同じ日に複数あればファイルを分ける。

```markdown
# YYYY-MM-DD タスク名

## やったこと
（何を変えたか。ファイル名は具体的に。PR・issueがあればリンク）

## 詰まった点 / 解決方法
（詰まらなかったなら「特になし」でよい。**なぜそうなったか**まで書く——
 「Xで失敗した→Yで直した」だけだと、次に同じ場面で再現できない）

## 次回への申し送り・知見
（次に同じ領域を触る人が知っていると得をすること。
 未解決のまま残したこと、意図的に先送りした判断とその理由）
```

## Step 1: 材料を集める

`git log --oneline` と `git diff --stat`（またはPRの差分）で、実際に何が変わったかを確認する。**会話の記憶だけで書かない**——やったつもりで終わっていることがある。

## Step 2: 書く

上のテンプレートに沿って書く。長さは1タスクあたり画面1つ分で足りる。作業の実況（「まずAを試して、次にBを試して」）は要らない。**結論と、次の人が知る必要のあることだけ**を残す。

## Step 3: 効く知見を昇格させる（この手順の本体）

**ここを飛ばすなら、記録を書く意味はほぼない。**

今回の「詰まった点」と「申し送り」を1つずつ見て、**次に同じ場面が来たとき、読まれる場所に書いてあるか**を判定する。書いていなければ、1〜2行に削って下表の反映先へ移す。あわせて過去の記録（`docs/history/` の直近数件）を見て、同じ指摘・同じ詰まりが2回以上出ていないかも確認する。2回出たものは、記録に書くだけでは止まらない。

| 繰り返しの内容 | 反映先 |
| --- | --- |
| レビューで毎回同じ指摘を受ける | `implementation-review` のチェックリスト |
| 特定の作業手順を毎回忘れる | 該当するスキル、または新しいスキル |
| プロジェクト固有の約束事（層の分け方、命名、起動手順） | `CLAUDE.md` |
| 安全に関わること（消してはいけないもの等） | `AGENTS.md` の安全ルール + 可能なら `permissions.deny` |

反映先が `AGENTS.md` や `.claude/settings.json` になる場合は、**安全網の変更なので勝手に書き換えず**、何をどう変えるか提案してユーザーの確認を得る。

昇格させるのは「次に同じ場面が来る」ものだけ。今回限りの事情（この日たまたま環境が壊れていた等）は昇格させない。`CLAUDE.md` は毎ターン読まれるので、**入れるほど全タスクが少しずつ高くなる**。1行に削れないものは、たいてい昇格に値しない。

昇格させたものは、記録側に「→ `CLAUDE.md` に昇格」と1行添える。同じ知見を次回また昇格させようとするのを防ぐため。

## Step 4: 索引を更新する

`docs/history/README.md` があれば1行追加する。無ければ作らなくてよい（記録が数件たまってから `doc-index` スキルで作る）。
