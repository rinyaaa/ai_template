# レビューは材料をファイルに束ね、対話と夜間実行で同じ担当を使う

## 背景

対話のレビュー（`impl-reviewer`）と夜間実行のレビュー（`night_runner.py` 専用の定義）が二重にあり、夜間の方はチェックリストも受け入れ条件も無く、毎ラウンド差分全体を読み直していた。レビュー担当はモデルを固定していた（opus / sonnet）。2026-11-09〜10 の会話（`WORK-slim-ai-harness`）で決めた。依頼の原文はその Work Item にある。

## 決定

- レビューの材料（依頼の原文・Work Item・関係するADR・チェックリスト・CLAUDE.md の固有の約束事・差分）は `scripts/review_bundle.py` が `.git/ai-review/bundle.md` に束ね、レビュー担当にはパスだけを渡す
- 判定は観点ごとの「満たす / 満たさない」と根拠。「ほぼ満たす」は満たさない。承認済みのADRとの食い違いは見送れない
- 再レビューは、初回レビュー時点の作業ツリーからの差分（修正分）だけを `impl-reviewer-recheck` が見る
- 夜間実行も同じ `impl-reviewer` / `impl-reviewer-recheck` を使い、issue を依頼の原文にする。night-run 専用のレビュー定義は持たない
- レビュー担当のモデルは固定しない（呼び出し元のモデルを使う。ユーザーの判断）

## 理由

- 材料をファイルにすれば、同じ diff を2回トークンとして流さない。修正分だけの再レビューで、ラウンドごとの読み直しが無くなる
- 担当を1つにすれば、夜間でも受け入れ条件とチェックリストに基づいて判定できる
- 比べた案: 夜間用の軽いレビューを残す → 二重管理で、夜間の方だけ品質が下がる
- 参考: 参考にした別プロジェクト の `review-changes`（規約・仕様・ADR の3つで見る、見送りの記録、ADRとの食い違いは見送り不可、依頼の原文 `## Source`）

## 影響

- 夜間実行は `origin/main` に戻すので、この仕組みが main にマージされていないと動かない。実際の夜間実行では未検証
- 再レビュー担当も呼び出し元のモデルで動くので、以前（sonnet 固定）より費用が上がることがある
- 依頼の原文が無い作業は「依頼の原文との一致」を判定できない（Work Item に原文を書く必要がある）
